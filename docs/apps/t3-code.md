# T3 Code: agent rules

Moved from `AGENTS.md`. User-facing steps are in the [README](../../README.md).

[Decision 0020](../decisions/0020-t3-code-through-omarchy-installer.md) is implemented (issue #110). The bun CLI path (`t3.codes/install.sh`, the known-good pin, `t3 update`, the CLI candidate check, and its repair) is gone. Do not bring it back.

- **Owner.** A new install runs `omarchy-install-ai-t3-code nightly --no-launch` once, when `~/.local/share/t3code/T3-Code.AppImage` is missing and `~/.local/bin/t3` is not the bun CLI's link. That installer is `requires-sudo` (it adds `fuse3`), so `privileged_changes_needed` counts a missing app, and the layer's one sudo prompt covers it. When the installer leaves no AppImage, setup stops before home changes, like a missing package. `omarchy-install-t3code-app` moves the AppImage in before `omarchy-install-ai-t3-code` runs it for its theme step, so a failing installer can leave a new build in place: that build is checked anyway, and setup reports either the failed check or the unfinished installer at the end. Setup also checks any installed AppImage that does not match `last-good.json` (one from Omarchy's menu, or one a failed install left), so a rerun never skips an unchecked build. Never run `omarchy pkg add t3code-bin` or `t3code-nightly-bin`.
- **The `t3` command** is the app's CLI, `${T3CODE_HOME:-~/.t3}/bin/t3`, linked from `~/.local/bin/t3` by Omarchy's installer. Before the app's first launch writes it, setup prints "Open T3 Code once" and checks nothing. After that, setup stops on PATH shadowing or a `t3 --version` that fails. On shadowing it also prints `scripts/groundwork-path-shadow.py t3`, which names the shell file that put the other `t3` first. A `t3` of the user's own at that path is left alone and reported once by setup.
- **The gate** (`t3_gate` in `scripts/groundwork-update.py`) runs only on pages larger than 4 KiB, from `update-all` (staged and installed) and from setup (`groundwork-update.py t3-check-installed <getconf PAGESIZE>`, installed only, with no older-build download because of setup's 900-second limit: it restores a kept copy, or says to run `update-all`). `t3_check_appimage` copies the AppImage into a `groundwork-t3-` temp directory under `~/.cache/groundwork` (disk, not a RAM-backed `/tmp`; removed after each check), verifies the sha512 when one is known, checks the AppImage runtime's own LOADs, unpacks it with `--appimage-extract` inside `t3_sandbox_command` (bubblewrap, read-only `/usr` and `/etc`, no home, no network, and for the extraction no IPC or UTS namespace either, scrubbed environment, core limit 1, 180 seconds), checks every EM_AARCH64 ELF under `squashfs-root` with `t3_load_segment_mappable` ([decision 0018](../decisions/0018-t3-load-segment-rule.md)), skips other machines' ELFs (node-pty `linux-x64/pty.node`), and smoke-runs `squashfs-root/t3code --version` in the same sandbox for 30 seconds. The version under test is the file name's (pending, feed), else the AppImage's `X-AppImage-Version` (a symlinked `t3code.desktop` is not read), else what the smoke run prints, and the smoke run must print it. A missing `bwrap` or `readelf` is a warning and runs nothing.
- **Results.** A misaligned LOAD (`misaligned-load`), a signal death while unpacking (`extract-crash`), or while smoke-running (`smoke-crash`) is written to `t3-rejected.json` with marker `"rule": "0020"`. A file with another marker (`0018`, or none) lists bun CLI builds; it is replaced by `{"rule": "0020"}` once, with one line naming the versions. A timeout, a transport error, a wrong version, a sha512 mismatch, or a SIGKILL (exit -9 or 137, most likely the OOM killer) warns and is not remembered.
- **Before an update.** `t3_check_pending` reads `~/.cache/t3code-updater/pending/update-info.json` (`fileName`, `sha512`). A file name that is not `T3-Code-<version>[-arm64].AppImage`, or a symbolic link, is a warning, and nothing is removed. A passing build stays staged. A failing one is removed by its exact path, together with `update-info.json`. Nothing else in that directory is touched. A staged file that does not match its sha512 is removed too, but not remembered. A version already rejected is removed again without a check.
- **After an update.** `t3_check_installed` skips a file whose sha512 matches `~/.local/state/groundwork/t3/last-good.json`. A build that passes is copied to `t3/T3-Code.AppImage` as the rollback. A failing one is replaced only when `groundwork-t3-launcher.py`'s `app_running` says no T3 Code process runs (unsure counts as running): first with that copy, else with the newest nightly that is not rejected (at most three tried), downloaded from its release's `nightly-linux-arm64.yml` with that sha512 and checked before `os.replace` puts it in place.
- **Known race.** The app may apply a staged build when it quits before `update-all` checks it. The next `update-all` finds the installed build failing and restores the copy. Rejected versions are held only by removing them from pending on each run. There is no pacman entry to pin.
- **Migration** (decision [0014](../decisions/0014-offer-migration-to-omarchy-installers.md), id `t3-cli`). `migrate_t3_cli_to_omarchy` in `scripts/apply-layer.sh` is offered when `~/.local/bin/t3` links into `~/.t3/runtime/versions/` and `omarchy-install-ai-t3-code` exists. It is refused, with nothing changed, while `groundwork-t3-launcher.py running` finds the app (AppImage path, `.mount_T3-Cod*`, or an `appimage_extracted_*/t3code`) or the bun CLI (`~/.t3/runtime/versions/`, also by its real path) running. `privileged_changes_needed` counts a migration that would install the app, so sudo is asked once up front. With the app missing it runs Omarchy's installer and the check first, and keeps the old link if either fails. With the app present it does not reinstall. Then it swaps the link atomically (`ln -s` to a temporary name, `mv -T`) to `~/.t3/bin/t3`. Omarchy's installer leaves a link that points elsewhere alone, so the swap is this layer's job. It keeps `~/.t3`, `~/.config/t3code*` and `~/.cache/t3code-updater`, records the old target in `~/.local/state/groundwork/t3-cli-switched` after a successful swap (a failed swap records nothing; a failed record puts the old link back), and prints `./install.sh --keep-standalone-t3` as the undo.
- **Automatic switch** (decision 0020's exception to 0014, issue #120). `auto_switch_t3_cli` runs before the offer on every setup and `update-all`. It switches only when all of these hold: no saved `t3-cli` decline and no marker `~/.local/state/groundwork/t3-cli-switched`; `T3CODE_INSTALL_BIN_DIR` unset or `~/.local/bin`; the link's target is under `${T3CODE_HOME:-~/.t3}/runtime/versions/` and `readlink -e` puts it on a file inside that directory; the AppImage is a file whose sha512 matches `last-good.json` (checked through the updater's `t3_last_good` and `t3_sha512`, so 4 KiB kernels, which write no record, keep the offer); `~/.t3/bin/t3` is an executable file; and `groundwork-t3-launcher.py running` exits 1. While something runs it prints one line and returns without the notice (a run with `--migrate-to-omarchy-installers` gets the offer's refusal instead). Any other failed guard falls through to the offer. The switch uses `switch_t3_link`, the swap the migration also uses: it writes the marker (the old target) after the swap, and prints `./install.sh --keep-standalone-t3` as the undo. Never print a bare `ln -sfn` for it: a hand-restored link would otherwise be switched again.
- **Undo.** `./install.sh --keep-standalone-t3` (setup only; refused with `--update` or `--migrate-to-omarchy-installers`) restores the marker's target when the link still points at `~/.t3/bin/t3` and the target, with every symlink and `..` resolved, is still an executable file under `runtime/versions` (anything else is refused with the link unchanged), then saves `t3-cli` in `declined_migrations` with the other setup choices. When the link is already the bun CLI's, it only saves the decline. With no marker it changes nothing and exits nonzero. `--migrate-to-omarchy-installers` clears the decline.
- Setup and `update-all` also run `scripts/groundwork-t3-launcher.py reconcile`, which points `x-scheme-handler/t3code` at the installer's `t3code.desktop` with `xdg-mime` and removes the app's self-registered duplicate `com.t3tools.T3Code.desktop` (the app re-creates it hidden with `NoDisplay=true`, which the Omarchy shell launcher honors). It reads Omarchy's entry layout (`Exec="<path>" %U` with `%` doubled, `TryExec=<path>`). It changes nothing, and says so, while a T3 Code process is running or cannot be ruled out. Its `running` command exits 0 when T3 Code (or the bun CLI) runs or that is unsure. Tests point it at a fixture `/proc` with `GROUNDWORK_TESTING=1 GROUNDWORK_TEST_PROC=<dir>`.
- Blip's bun preflight calls the T3 `load_alignments` helper (see [Blip](blip.md)).

## Omarchy-first evidence

Checked 2026-10-31. Omarchy has its own installer for T3 Code: `omarchy-install-ai-t3-code [stable|nightly]` (Install > AI > T3 Code). It installs the self-updating AppImage at `~/.local/share/t3code/T3-Code.AppImage` and drops the feed packages. The pkgs.omarchy.org `edge/aarch64` feed still builds `t3code-bin 0.1.5-1` and `t3code-nightly-bin 0.1.6_nightly.20261031.3956-1`, but Omarchy treats them as the old path (migration `1792345511` replaces them). [Decision 0020](../decisions/0020-t3-code-through-omarchy-installer.md) records the evidence: package contents, ELF LOAD results under both alignment rules, and smoke runs. It also records why this layer uses the installer, not the packages. Recheck by 2026-11-30.
