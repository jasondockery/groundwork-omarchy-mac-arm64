# 0015. Brave through Omarchy's browser installer

Checked 2026-10-30. The shared choice of Brave, the policy rows, and the one offered extension live in groundwork-core, in `browser/brave.json` and [`docs/browser.md`](https://github.com/jasondockery/groundwork-core/blob/main/docs/browser.md). This repo pins a groundwork-core tag as the `core` submodule; the tag is the `branch =` line of `[submodule "core"]` in `.gitmodules`, and the gitlink must be that tag's commit. Renovate proposes tag bumps. It does not keep a second copy of the spec. `./install.sh` and the updater in the checkout run `git submodule update --init -- core` after a fast-forward and before apply reads the file. `scripts/apply-layer.sh` runs that same checkout when `core/browser/brave.json` is missing or is a symlink, before it refuses an incomplete checkout. An `update-all` installed by an earlier apply execs that older program: it fast-forwards, then runs this script, and the checkout in the script is what lets that first run succeed and replace the installed updater. A worktree still at an older gitlink is updated; that drift is not a local change. Edits inside `core` are. This decision owns only the Apple Silicon Omarchy install.

Brave release is the browser this layer offers. Brave Origin (`omarchy-install-browser brave-origin`) is a different browser and is not installed. Chromium stays; it is part of the Omarchy base, and this layer never removes it. There is no Flatpak of Brave: Brave's Linux page says the Flatpak is not yet working as well as the native package, and this layer does not add one when `brave-bin` fails.

## Install

When `brave` is missing and `omarchy-install-browser` with no arguments prints a usage line that contains `|brave|`, setup runs `omarchy-install-browser brave`. That is Omarchy's installer for the AUR package `brave-bin`. When that command is absent, or its usage line has no `brave`, nothing is installed and nothing is offered. That installer ends with a blank line and "Brave browser installed. Make it the default via Setup > Defaults > Browser." Setup drops those two lines, because it checks Brave next and then sets or keeps the default itself and says which. Every other line of the installer's output is shown unchanged.

A `brave` already on `PATH` that `pacman -Qoq` does not report as `brave-bin`, and the user Flatpak `com.brave.Browser`, are not replaced by a silent install. They are offers, below.

## Checks

After a `brave-bin` command is on `PATH`, setup checks it before offering it as the default:

- Every ELF file `pacman -Qlq brave-bin` lists is checked with `readelf -lW`, the same LOAD-alignment check as Bitwarden and local inference. A package with no ELF file fails this check. The reference mini uses 16 KiB pages. The known crash is [brave/brave-browser#42312](https://github.com/brave/brave-browser/issues/42312). This layer does not pass `--js-flags=--nodecommit_pooled_pages`.
- A short launch opens a real Brave window, the same path a person's launch takes: Wayland, the GPU process, and a page, with no `--headless` and no `--disable-gpu`. It runs the `brave` on `PATH` with `--ozone-platform=wayland --password-store=basic --no-first-run --no-default-browser-check --disable-extensions --disable-background-networking --disable-component-update --user-data-dir=<temporary> --remote-debugging-pipe about:blank`. The environment is a private `HOME`, `TMPDIR`, `XDG_RUNTIME_DIR`, and other `XDG_*` directories in one temporary directory, `PATH=/usr/bin:/bin`, `LANG=C.UTF-8`, and `WAYLAND_DISPLAY` set to the absolute path of this session's Wayland socket. Nothing else from the caller is passed: no D-Bus address, keyring, X11 display, or the caller's runtime directory, and no other open file descriptor. Setup says the window will open before it runs. The check talks to Brave over the DevTools pipe on file descriptors 3 and 4; no port is opened. Brave must answer within 30 seconds, stay up for 5 seconds with its window open, then close through `Browser.close` and exit 0 within 15 seconds. Stdout and stderr are discarded, and the temporary directory, including the throwaway profile and any crash report in it, is deleted. The user's Brave profile is not the one this launch opens. The child runs with `RLIMIT_CORE` soft and hard set to 1. A piped core pattern, including systemd-coredump, writes a core for every other limit and treats 0 as unlimited. Ctrl+C while that check is running stops setup with exit 130. That interrupt is not a Brave result: the version is not remembered, and setup does not continue.
- The launch needs the desktop session. When `WAYLAND_DISPLAY` is unset, or does not name a socket this user owns (SSH or cron), the launch is not run. That is a retried result, below, and the line says to run `update-all` from a terminal on the desktop.

The earlier check was a headless launch with `--disable-gpu` in an environment with no session variables. On the reference mini (2026-10-30, `brave-bin` 1:1.98.62-1) that launch never exited when it was given `--user-data-dir`, with or without D-Bus, so every check timed out, and it could not see a crash on the windowed or GPU path at all.

A failed alignment, a missing ELF, or a launch that dies by a crash signal (SIGSEGV, SIGTRAP, SIGABRT, SIGBUS, SIGILL, or SIGFPE, as exit above 128 or a negative code) while opening, while its window is open, or while closing, is remembered in `~/.local/state/groundwork/brave-rejected.json`, keyed by page size, the same way as `bitwarden-rejected.json`. The version is the installed `pacman -Q brave-bin` version, or else the one `pacman -Si brave-bin` offers. A version already in that file is not installed or checked again, including by the Flatpak or foreign-command migration. That offer is not shown while the version `pacman -Si` would install is still rejected. A copy this run added is removed with `omarchy-remove-browser brave`. A copy that was already installed is left in place. Setup prints one line saying why, what it remembered, whether it removed the copy, and the default. When `omarchy default browser` prints `brave`, that line says Brave stays the default and names `omarchy default browser chromium`. Otherwise it says Chromium stays the default.

A launch timeout, a launch stopped by any other signal (SIGKILL from the OOM killer, SIGTERM or SIGHUP at logout), a missing desktop session, a window that does not close in time, a checker error before the process can be classified, or any other non-zero exit that is not a signal, is not remembered and is not removed. Setup prints the line and tries that version again on the next run. The line names whichever browser is actually the default. A failed `omarchy-install-browser brave` is also not remembered. If that command returns success but `brave-bin` does not own the `brave` on `PATH`, the copy this run added is removed and the version is not remembered.

A version that passes both checks is recorded in `brave-accepted.json` for that page size. The first version to pass on a page size is recorded after the default step below, so a run stopped between the check and that step checks again next time and still makes the one switch. A later `brave-bin` version is checked again. Passing once is not a pass for the next build.

If `brave-rejected.json` or `brave-accepted.json` exists and is not a regular file mapping page size to lists of versions, setup prints that path and stops before `omarchy-install-browser`. A missing file means the version is not remembered. A damaged accept file cannot be treated as a pass.

## Default and migration

Groundwork decides the default once (Jason, 2026-10-30, issues #75 and #78, approved on PR #86). This is the shared rule in groundwork-core [`docs/browser.md`](https://github.com/jasondockery/groundwork-core/blob/main/docs/browser.md#setting-the-default) ([groundwork-core#37](https://github.com/jasondockery/groundwork-core/pull/37)), which every OS follows. The first time a `brave-bin` passes both checks on this page size, which is when `brave-accepted.json` had no version for it before, and `omarchy default browser` prints `chromium` or nothing (no default set, which counts as one the person did not choose), setup runs `omarchy default browser brave` itself and prints one line saying Brave is the default and how to switch back. That happens on `./install.sh` and on updates, with or without a terminal. It does not happen when `default-browser-brave` is already in `declined_migrations`, or when the default is a browser other than Chromium; those get the offer below. After that first time, a default the user picks is left alone: a later `brave-bin` version that passes is not a reason to switch again. When `omarchy default browser brave` fails, setup prints one line, keeps going, and the default stays what it was. The default is never changed for a Brave that failed or was not checked.

Other offers use the helper from [decision 0014](0014-offer-migration-to-omarchy-installers.md). One flag, `./install.sh --migrate-to-omarchy-installers`, still runs every offer that is pending.

- `default-browser-brave`. When Brave passed both checks, setup did not just make it the default, and `omarchy default browser` does not print `brave`, setup offers to run `omarchy default browser brave`. `./install.sh` in a terminal asks `[y/N]`. A yes is the only answer that changes the default. Updates and runs without a terminal print one line and do not ask. A no is saved in `declined_migrations`.
- `brave-flatpak`. A user Flatpak `com.brave.Browser`, or a `brave` command `brave-bin` does not own, is reported in one line. Migration runs `omarchy-install-browser brave` and the checks above. It does not uninstall the Flatpak, does not pass `--delete-data`, and leaves `~/.var/app/com.brave.Browser` in place. Import with `brave://settings/importData`.

`omarchy-remove-browser brave` removes the package this run added. It does not delete `~/.config/BraveSoftware`. This layer never removes Chromium.

Once Brave is the default, web apps opened with `omarchy-launch-webapp` follow the default browser, so they open in Brave. Sign-ins that exist only in Chromium's profile stay there.

A routine update installs a missing Brave only through the same sudo gate as other privileged changes. Without a terminal and without cached sudo, the update stops before installing it. An already installed `brave-bin` asks for sudo only when its policy is not current. A launch retry does not. This layer does not upgrade Brave; `omarchy update` does.

## Policies and Bitwarden

When `brave-bin` owns the `brave` on `PATH`, setup writes `core/browser/brave.json` to `/etc/brave/policies/managed/groundwork.json`. The file is the policy names and values only. Reasons stay in the spec. Directories are `0755` and the file is `0644`, both `root:root`, via `sudo install`. An unchanged file is not written again. When the bytes already match and the owner or mode does not, setup runs `sudo chown root:root` and `sudo chmod 644` and does not rewrite the file. `omarchy.json` and `color.json` in that directory are left alone. A symlink anywhere on that path is refused. A decline from the same run is saved before that refusal. Root ownership is what survives Omarchy's `browser_policy_purge_dir`, which deletes non-root files in the managed directory.

The Bitwarden extension id and update URL are read from that same spec. Setup still registers only that extension, `nngceckbapebfimnlniiiahkandclblb`, at `/usr/share/chromium/extensions`, as an external manifest. It does not add `ExtensionInstallForcelist`. Brave is not Google-branded and reads that same Chromium directory: on the reference mini on 2026-10-30, a fresh Brave profile installed Bitwarden from it. The line setup prints names the browsers the manifest is registered for: Chromium and Brave when `brave-bin` owns the `brave` on `PATH`, otherwise Chromium alone. If Brave ever ignores that directory, the machine report says so. The fix is not a forced install.

## Crash on the reference mini (issue #76)

On 2026-10-30 two windowed Brave launches on the mini dumped core about 12 seconds in with SIGTRAP (a Chromium `CHECK`) in the browser process, not the GPU process. The two Crashpad reports carry the crash key `tabdrag-event-source=mouse`, which Chromium sets only when a tab drag starts, and they report GPU compositing through ANGLE on Mesa 26.2.6 for the Apple M1 GPU. Later that day the same `brave-bin` 1:1.98.62-1 ran a 3 minute 47 second session, ran 25 and 40 second windowed launches with the user's flags, and passed the check above with GPU compositing enabled. So the crash is tied to dragging a tab on Hyprland, not to starting Brave, the GPU, the 16 KiB-page bug, or the managed policy, which was in place for every launch that worked. A tab-drag crash is Brave's or Chromium's to fix upstream. The launch check cannot drag a tab and does not claim to catch it.
