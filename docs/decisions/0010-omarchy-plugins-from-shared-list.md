# 0010. Apply Omarchy shell plugins from the shared list

Default shell plugins for every `groundwork-omarchy-*` checkout live in one list, `groundwork-core/omarchy/plugins.json`. This repo applies that list. It does not name plugin ids, vendor plugin checkouts, or Stow `~/.config/omarchy/shell.json`.

`scripts/omarchy-plugins.py` is the only applier. `scripts/apply-layer.sh` calls it once, immediately after the Hyprland reload block. `GROUNDWORK_PLUGIN_LIST` selects a local file or an https URL. Otherwise the helper fetches `https://raw.githubusercontent.com/jasondockery/groundwork-core/main/omarchy/plugins.json`. The download allows only https, rejects a redirect whose scheme is not https, and rejects an https redirect whose host is not the starting host, `raw.githubusercontent.com`, `objects.githubusercontent.com`, or `github.com`. A rejected redirect keeps the saved copy. The socket timeout is the time remaining on a 20 second deadline before each read. The last valid document is cached at `$XDG_STATE_HOME/groundwork/omarchy-plugins.json` (default `~/.local/state/groundwork/omarchy-plugins.json`). An invalid list, an unreachable host, or an HTTP client error falls back to that copy. With neither a list nor a cache, the helper prints one line and exits 0 so the rest of apply continues. Before it changes plugins, it prints what changed relative to the cache.

The document must use `schemaVersion` 1 or 2 as a JSON number. Version 2 adds built-in plugins and `replaces`; a version 1 document is read as before. Ids match `^[A-Za-z0-9][A-Za-z0-9._-]*$`, contain no `..`, and, for cloned entries, do not start with `omarchy.` (case-sensitive, matching Omarchy). A `builtIn` entry may use that prefix. `repo` is `https://github.com/<owner>/<name>` with an optional `.git` suffix. `retired` is required. Unknown plugin fields are ignored so the shared list can grow. A `section` other than `left`, `centerBegin`, `center`, `centerEnd`, `tray`, or `right` skips that entry. The helper prints one line with its id, then applies and caches the rest. Those are the sections `omarchy plugin enable` accepts on `quattro` since Omarchy Mac converged into upstream Omarchy (omacom/omarchy#14431). A bad id, a bad repo, a `plugins` value that is not a list, or a missing `retired` list still rejects the whole document. Invalid sections stay out of the command line.

Entries are skipped when `arch` does not include `uname -m`, and when the id appears in `omarchy-plugins.exclude.json` or `$XDG_CONFIG_HOME/groundwork/omarchy-plugins.exclude.json` (default `~/.config/groundwork/omarchy-plugins.exclude.json`). Each exclusion is an id and a reason. An invalid exclusion file skips every plugin change for that run.

For a selected id, an existing `~/.config/omarchy/plugins/<id>` directory is left in place. That covers a plugin the user installed, disabled, or updated by hand. The helper never rewrites `shell.json` and does not read enablement from it; the only read is the bar layout slot of a replaced widget, described below. A missing directory is installed only while `omarchy-shell shell ping` returns `ok`. The helper runs `omarchy plugin add <repo> --yes`, checks that the new directory's manifest id matches the list, and then runs `omarchy plugin enable <id>` with `--section` when the entry sets one. `add --enable --yes` is not used: with `--yes`, Omarchy skips the section prompt, and this layer still has to place the plugin. The manifest is checked before enable so a mismatched id is not turned on. A mismatch removes the checkout this run just added and continues with the next entry. After enable succeeds, the id is recorded in `$XDG_STATE_HOME/groundwork/omarchy-plugins-installed.json`. A checkout that still needs enable is recorded with `enablePending` instead.

A version 2 entry with `builtIn: true` names a plugin that ships with Omarchy, such as a built-in agents widget. It may use the `omarchy.` prefix, must not set `repo` or `setup`, and has no checkout to add, update, or remove. While the shell runs, the helper reads `omarchy plugin list --json`. A built-in that the shell does not list as first-party is skipped with one line. One that is already enabled is recorded and keeps its placement. One that is disabled is enabled once with `omarchy plugin enable <id>`, with `--section` only when the entry sets one. The record stores `builtIn: true` without a repo, plus `enabledHere: true` only when this layer ran enable. A recorded built-in is never enabled again, so a widget the user turned off stays off. A retired built-in is disabled with `omarchy plugin disable <id>` only when `enabledHere` is set and `omarchy plugin list --json` shows it enabled. Otherwise, including when the shell does not list it, the record is just dropped, so a widget that was already on is left on. The record may therefore hold `omarchy.` ids. An older applier validates records strictly, rejects such a record as invalid, and skips plugin changes until it is updated. The record's `schemaVersion` is not bumped.

The record may also hold `replacedAt`, a list of `{id, section, index}` objects whose ids all appear in `replaced`, with a known section and a non-negative integer index. A malformed `replacedAt` invalidates the whole record, and the helper skips plugin changes for that run. An older applier (as of bc60552) drops `replacedAt` silently from a cloned plugin's record and rewrites the record without it on its next save, so the stored slots are lost and a later restore uses Omarchy's default placement. It rejects `replacedAt` on a built-in record as invalid and skips plugin changes until it is updated.

The record also says which replaced ids this layer turned off itself. `disabledHere` lists ids whose own `omarchy plugin disable` this layer ran and saw succeed. `disabling` lists ids it saw on and was about to disable. Both are lists of distinct ids from `replaced`, no id is in both, and `disabledHere` is always written beside a non-empty `replaced` (an empty list when none), so a record without it is known to come from an applier before these marks. A malformed mark, or `disabling` without `disabledHere`, invalidates the whole record, and the helper skips plugin changes for that run. A record written before the marks (as of b1703b5) is read with one rule: an id with a stored slot counts as disabled here, because that applier stored a slot only after its own disable succeeded and copied it only on a hand-over, and an id without a slot does not, because it may have been off already (that applier also recorded those) and when in doubt the user's state wins. That leaves off a widget an older applier did disable while `shell.json` gave no slot, including every swap recorded by an applier before b1703b5, which stored no slots. An older applier drops both marks silently from a cloned plugin's record and rejects them on a built-in record, as with `replacedAt`.

A version 2 entry may set `replaces` to plugin ids it supersedes, such as a spaces plugin replacing the built-in workspaces widget. The ids come from the shared list, so this repo still names none. After this layer has recorded the replacing plugin and the shell lists it as enabled, the helper runs `omarchy plugin disable` once for each replaced id that is still enabled. Just before each disable it reads the widget's section and index from `bar.layout` in `~/.config/omarchy/shell.json`, scanning sections in Omarchy's own order. It uses that file only when it parses to an object with `version: 1`, which is the condition under which the shell uses it; otherwise no slot is stored. Right before the disable it reads `omarchy plugin list --json` again and goes on only if the widget is still on. It then saves the id, its slot, and a `disabling` mark, runs the disable, waits briefly (up to two seconds) for the shell to write the layout without the widget, and saves the id as `disabledHere`. A widget the shell lists as off, or does not list, and that no record holds is recorded without a mark, so the swap is not repeated and turning the widget on later sticks. A failed disable keeps the `disabling` mark, because the command may have turned the widget off before it failed. The record stores the ids as `replaced` and the slots as `replacedAt`, a list in capture order, and never repeats the swap, so turning the replaced widget back on sticks. A replaced id in the exclusions is never disabled. If the user has turned the replacing plugin off, the original stays on. A `replaces` value that is added to an entry already installed applies on the next run. When a plugin with a recorded `replaced` list is retired, the helper removes or disables it, then runs `omarchy plugin enable` for each replaced id that this layer disabled (`disabledHere`), that the shell lists as disabled, and that no other entry takes over (below), passing `--section` and `--index` from `replacedAt` so the widget returns to its old slot, and drops the record. Slots are restored in reverse capture order, so each index meets the layout it was measured against; a widget without a stored slot gets Omarchy's default placement. Omarchy drops a widget's per-widget settings across a disable and enable, so only the position returns. Jason approved the broader rule on 2026-10-28 (#53): this layer only undoes what it did. On every run, a recorded `replaced` id that its record's entry no longer replaces and that no other entry takes over (below) is pruned from every record, after it is turned on again in its stored slot when this layer disabled it and the shell lists it as off. That covers an entry that drops the id or the whole `replaces` field, a replacing entry that left the list without being retired, a replacing plugin the user excludes, and a replacing plugin that does not apply on this machine's architecture. When the architecture cannot be read, an arch-limited entry still counts as replacing its ids, so an unreadable architecture never undoes a swap. An id the user turned back on, one the shell no longer lists, and one that was already off when it was recorded are only pruned. The restore waits (one deferral line) when the shell is down or its listing has no first-party plugin, because the listing can be empty or partial while the shell starts; a failed enable prints its own failure line and is retried next run. Slotted widgets are restored first, in reverse capture order, and widgets without a slot after them, so default placements cannot shift an exact slot.

Two entries can replace the same widget. A second entry never records or disables an id another record already holds, even after the user turned it back on. When a record lets go of an id, whether by dropping it, leaving the list, or retirement, the id, its slot, and its `disabledHere` mark move to another listed entry only when that entry would disable the id itself now: this layer recorded it, its enable finished (no `enablePending`), the shell lists it as on, and the user has not excluded the id. An arch-limited entry counts when the architecture cannot be read, so that gap never undoes a swap such an entry can hold. Otherwise the widget is turned on again in its slot and the id is pruned, even when a listed entry that has not applied yet still replaces it. That entry has changed nothing yet. When it applies, later in the same run or on a later one, it disables the widget once and measures the slot again, so the widget blinks once and keeps its place; if it never applies, the widget stays on. A record still waiting for enable holds no swap; if an earlier applier gave it one, that id is let go of the same way, and the record is not dropped while it holds the id. A restore uses the slot from the record that has one, preferring the record that lets go, and prunes the id from every record. The invariant: every widget this layer disabled is either held by exactly one applied record (recorded, enable finished) or restored. An undo that cannot finish this run, because the shell is down, its listing is not ready, or an enable fails, keeps the holding record, including a retired one, for the next run. The rule, from Jason's decision on 2026-10-28 (#66): the user's Omarchy widget state is authoritative. A widget the user turned off stays off, and this layer never turns on a widget it did not turn off itself. It changes widget state only through `omarchy plugin enable` and `omarchy plugin disable`, reads that state from `omarchy plugin list --json`, and reads `shell.json` only for a slot. Its marks exist only to know what it may undo, and when in doubt it leaves the widget as the user has it. So an id recorded without `disabledHere` is pruned on any undo (retirement, a drop, an exclusion, `arch`, or a hand-over that falls back to a restore) and the widget stays off.

An interrupted disable is settled on the next run that gets a complete listing, before anything reads the marks. The `disabling` mark is written only after this layer saw the widget on a moment earlier, immediately before its own disable. If the run stops after the disable (the widget is off and the confirmation was not saved), the next run finds the widget off and marks it `disabledHere`, so a later undo restores it in the slot saved with the intent. If the run stops before the disable (the widget is still on), the next run finds it on, lets go of the id, and the swap runs once with a fresh slot. A widget the shell no longer lists is let go of. Two narrow cases remain where off is read as this layer's doing although the user did it: the user turns the widget off in the milliseconds between that last listing and the disable, or the run stops between the intent save and the disable and the user turns the widget off before the next run. Both need a user toggle of that widget inside one automated step, so they are accepted; the user turns it off again if an undo turns it on. Without a mark of either kind, an off widget is never treated as this layer's. A replaced id the user excludes after the swap is still restored when one of those undo events happens, because the exclusion stops this layer from disabling the id and does not stop it from undoing its own change; the exclusion alone restores nothing. An excluded replaced id is skipped without a message by the replacement step; an excluded id that is also a list entry in its own right is still named once per run in the "Skipped" line, by design. Without a plugin listing, the retirement is deferred.

`omarchy plugin add` asks the shell to rescan but does not wait, so `omarchy plugin enable` can refuse a fresh checkout as "not known" (#79). When enable fails that way, the helper runs `omarchy-shell shell rescanPlugins` and waits up to 10 seconds (`GROUNDWORK_PLUGIN_RESCAN_WAIT`, in seconds) for `omarchy plugin list --json` to show the id, then retries enable once. If the shell still does not list it, the checkout is kept and recorded `enablePending`, no further plugins are cloned that run, and one line names the count and the next step (restart the Omarchy shell, run `update-all` again) instead of one failure per plugin. The next run retries enable only. Any other enable failure still removes the checkout this run added, as below.

A failed add that leaves no directory leaves no record, so the next run retries it. If `omarchy plugin add` creates the directory and then exits non-zero, this run records `enablePending` and retries enable before continuing with the next entry. If that enable fails, the new directory is removed. A failed enable removes the plugin this run just added, because `add` is not idempotent while the directory exists. If `omarchy plugin remove` exits non-zero but the directory is gone, the record is dropped and the next run adds again. If the directory remains, the record keeps `enablePending` and the next run retries enable only. An `enablePending` record whose directory is already missing is dropped, and add runs. A directory that was already present is never removed and never enabled again. A recorded id whose directory is gone, other than `enablePending`, was removed locally and stays uninstalled.

`setup.command` runs from `<plugin-dir>/<command>`, after the install this layer recorded, and only when stdin and stdout are both terminals. The command is a relative path inside the plugin directory. With `needsSudo`, the helper uses `sudo -n true` when this apply already has a cached credential, and otherwise prompts once with `sudo -v` on `/dev/tty`. That prompt lives in this helper. The setup script then runs as the current user, so its own sudo calls reuse the warm timestamp. `privileged_changes_needed` runs before the Hyprland block and cannot see plugin setup commands without a second pass over the list; issue #18 also owns that area. Without a terminal, or when sudo cannot be primed, the helper prints the script path. A setup that is due and does not finish is stored with `pending: true` and runs on the next apply. That covers a deferral, a failed script, and a timeout. A finished setup runs again after this layer's `omarchy plugin update` moves `HEAD`, including when that command exits non-zero after the revision changes. A commit made by hand inside the checkout does not.

`update-all` is the only command that updates plugin checkouts. It passes `--update-plugins` into `apply-layer.sh`, which then calls the helper with `--update`. Configuration-only `groundwork-update` uses `--update` for saved setup choices and does not pass `--update-plugins`, so existing checkouts stay at their current revisions. Updates run `omarchy plugin update <id> --yes` for listed ids that are already installed. `omarchy update` does not update plugins.

Retired ids are removed with `omarchy plugin remove <id> --yes` only when this layer recorded the install. Every other retired id whose plugin directory exists gets one notice and stays on disk. The helper records that notice, and later runs stay quiet for that id. A retired id with no directory is left unmentioned. Removal still happens when the id is excluded. Without a shell session, installs, enables, updates, and removals are deferred and retried next run. One plugin failure prints a line and leaves the rest of apply running.

If `~/.config/hypr/mouse.lua` or `omacontrol.lua` sets `touchpad.natural_scroll` differently from the stowed `packages/hypr/.config/hypr/input.lua`, the helper warns. When `~/.config/hypr/hyprland.lua` requires `hypr.mouse` or `hypr.omacontrol`, the warning names the file loaded later; that file wins. When `hyprland.lua` does not load the differing file, the warning says so and the stowed `input.lua` still applies. The value read is the last `natural_scroll` inside the `touchpad` table. A missing key in the stowed file is upstream's `false`. See [decision 0007](0007-learn-omarchy-defaults.md).
