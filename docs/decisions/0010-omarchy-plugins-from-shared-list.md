# 0010. Apply Omarchy shell plugins from the shared list

Default shell plugins for every `groundwork-omarchy-*` checkout live in one list, `groundwork-core/omarchy/plugins.json`. This repo applies that list. It does not name plugin ids, vendor plugin checkouts, or Stow `~/.config/omarchy/shell.json`.

`scripts/omarchy-plugins.py` is the only applier. `scripts/apply-layer.sh` calls it once, immediately after the Hyprland reload block. `GROUNDWORK_PLUGIN_LIST` selects a local file or an https URL. Otherwise the helper fetches `https://raw.githubusercontent.com/jasondockery/groundwork-core/main/omarchy/plugins.json`. The download allows only https, rejects a redirect whose scheme is not https, and rejects an https redirect whose host is not the starting host, `raw.githubusercontent.com`, `objects.githubusercontent.com`, or `github.com`. A rejected redirect keeps the saved copy. The socket timeout is the time remaining on a 20 second deadline before each read. The last valid document is cached at `$XDG_STATE_HOME/groundwork/omarchy-plugins.json` (default `~/.local/state/groundwork/omarchy-plugins.json`). An invalid list, an unreachable host, or an HTTP client error falls back to that copy. With neither a list nor a cache, the helper prints one line and exits 0 so the rest of apply continues. Before it changes plugins, it prints what changed relative to the cache.

The document must use `schemaVersion` 1 or 2 as a JSON number. Version 2 adds built-in plugins and `replaces`; a version 1 document is read as before. Ids match `^[A-Za-z0-9][A-Za-z0-9._-]*$`, contain no `..`, and, for cloned entries, do not start with `omarchy.` (case-sensitive, matching Omarchy). A `builtIn` entry may use that prefix. `repo` is `https://github.com/<owner>/<name>` with an optional `.git` suffix. `retired` is required. Unknown plugin fields are ignored so the shared list can grow. A `section` other than `left`, `centerBegin`, `center`, `centerEnd`, `tray`, or `right` skips that entry. The helper prints one line with its id, then applies and caches the rest. Those are the sections `omarchy plugin enable` accepts on `quattro` since Omarchy Mac converged into upstream Omarchy (omacom/omarchy#14431). A bad id, a bad repo, a `plugins` value that is not a list, or a missing `retired` list still rejects the whole document. Invalid sections stay out of the command line.

Entries are skipped when `arch` does not include `uname -m`, and when the id appears in `omarchy-plugins.exclude.json` or `$XDG_CONFIG_HOME/groundwork/omarchy-plugins.exclude.json` (default `~/.config/groundwork/omarchy-plugins.exclude.json`). Each exclusion is an id and a reason. An invalid exclusion file skips every plugin change for that run.

For a selected id, an existing `~/.config/omarchy/plugins/<id>` directory is left in place. That covers a plugin the user installed, disabled, or updated by hand. The helper never rewrites `shell.json` and does not read enablement from it; the only read is the bar layout slot of a replaced widget, described below. A missing directory is installed only while `omarchy-shell shell ping` returns `ok`. The helper runs `omarchy plugin add <repo> --yes`, checks that the new directory's manifest id matches the list, and then runs `omarchy plugin enable <id>` with `--section` when the entry sets one. `add --enable --yes` is not used: with `--yes`, Omarchy skips the section prompt, and this layer still has to place the plugin. The manifest is checked before enable so a mismatched id is not turned on. A mismatch removes the checkout this run just added and continues with the next entry. After enable succeeds, the id is recorded in `$XDG_STATE_HOME/groundwork/omarchy-plugins-installed.json`. A checkout that still needs enable is recorded with `enablePending` instead.

A version 2 entry with `builtIn: true` names a plugin that ships with Omarchy, such as a built-in agents widget. It may use the `omarchy.` prefix, must not set `repo` or `setup`, and has no checkout to add, update, or remove. While the shell runs, the helper reads `omarchy plugin list --json`. A built-in that the shell does not list as first-party is skipped with one line. One that is already enabled is recorded and keeps its placement. One that is disabled is enabled once with `omarchy plugin enable <id>`, with `--section` only when the entry sets one. The record stores `builtIn: true` without a repo, plus `enabledHere: true` only when this layer ran enable. A recorded built-in is never enabled again, so a widget the user turned off stays off. A retired built-in is disabled with `omarchy plugin disable <id>` only when `enabledHere` is set and `omarchy plugin list --json` shows it enabled. Otherwise, including when the shell does not list it, the record is just dropped, so a widget that was already on is left on. The record may therefore hold `omarchy.` ids. An older applier validates records strictly, rejects such a record as invalid, and skips plugin changes until it is updated. The record's `schemaVersion` is not bumped.

The record may also hold `replacedAt`, a list of `{id, section, index}` objects whose ids all appear in `replaced`, with a known section and a non-negative integer index. A malformed `replacedAt` invalidates the whole record, and the helper skips plugin changes for that run. An older applier (as of bc60552) drops `replacedAt` silently from a cloned plugin's record and rewrites the record without it on its next save, so the stored slots are lost and a later restore uses Omarchy's default placement. It rejects `replacedAt` on a built-in record as invalid and skips plugin changes until it is updated.

A version 2 entry may set `replaces` to plugin ids it supersedes, such as a spaces plugin replacing the built-in workspaces widget. The ids come from the shared list, so this repo still names none. After this layer has recorded the replacing plugin and the shell lists it as enabled, the helper runs `omarchy plugin disable` once for each replaced id that is still enabled. Just before each disable it reads the widget's section and index from `bar.layout` in `~/.config/omarchy/shell.json`, scanning sections in Omarchy's own order. It uses that file only when it parses to an object with `version: 1`, which is the condition under which the shell uses it; otherwise no slot is stored. After the disable it waits briefly (up to two seconds) for the shell to write the layout without the widget, then saves the record so an interruption keeps the slot. The record stores the ids as `replaced` and the slots as `replacedAt`, a list in capture order, and never repeats the swap, so turning the replaced widget back on sticks. A replaced id in the exclusions is never disabled. If the user has turned the replacing plugin off, the original stays on. A `replaces` value that is added to an entry already installed applies on the next run. When a plugin with a recorded `replaced` list is retired, the helper removes or disables it, then runs `omarchy plugin enable` for each replaced id that the shell lists as disabled, passing `--section` and `--index` from `replacedAt` so the widget returns to its old slot, and drops the record. Slots are restored in reverse capture order, so each index meets the layout it was measured against; a widget without a stored slot gets Omarchy's default placement and is enabled first. Omarchy drops a widget's per-widget settings across a disable and enable, so only the position returns. Jason approved the broader rule on 2026-10-28 (#53): this layer only undoes what it did. On every run, a recorded `replaced` id that no listed entry still replaces and that the shell lists as off is turned on again in its stored slot, then pruned from every record. That covers an entry that drops the id or the whole `replaces` field, a replacing entry that left the list without being retired, a replacing plugin the user excludes, and a replacing plugin that does not apply on this machine's architecture. When the architecture cannot be read, an arch-limited entry still counts as replacing its ids, so an unreadable architecture never undoes a swap. An id the user turned back on, or that the shell no longer lists, is only pruned. The restore waits (one deferral line) when the shell is down or its listing has no first-party plugin, because the listing can be empty or partial while the shell starts; a failed enable prints its own failure line and is retried next run. Slotted widgets are restored first, in reverse capture order, and widgets without a slot after them, so default placements cannot shift an exact slot.

One id can be held by two records, for example when two entries replace the same widget. A second entry never records an id another record already holds. When a record lets go of an id that another listed, recorded entry still replaces, whether by dropping it, leaving the list, or retirement, the id and its slot move to that entry's record and the widget stays off. If that entry is not recorded yet, a retiring record forgets the id and a live record keeps it. A restore uses the slot from the record that has one and prunes the id from every record. A replaced id the user excludes after the swap is still restored when one of those undo events happens, because the exclusion stops this layer from disabling the id and does not stop it from undoing its own change; the exclusion alone restores nothing. An excluded replaced id is skipped without a message by the replacement step; an excluded id that is also a list entry in its own right is still named once per run in the "Skipped" line, by design. Without a plugin listing, the retirement is deferred.

A failed add that leaves no directory leaves no record, so the next run retries it. If `omarchy plugin add` creates the directory and then exits non-zero, this run records `enablePending` and retries enable before continuing with the next entry. If that enable fails, the new directory is removed. A failed enable removes the plugin this run just added, because `add` is not idempotent while the directory exists. If `omarchy plugin remove` exits non-zero but the directory is gone, the record is dropped and the next run adds again. If the directory remains, the record keeps `enablePending` and the next run retries enable only. An `enablePending` record whose directory is already missing is dropped, and add runs. A directory that was already present is never removed and never enabled again. A recorded id whose directory is gone, other than `enablePending`, was removed locally and stays uninstalled.

`setup.command` runs from `<plugin-dir>/<command>`, after the install this layer recorded, and only when stdin and stdout are both terminals. The command is a relative path inside the plugin directory. With `needsSudo`, the helper uses `sudo -n true` when this apply already has a cached credential, and otherwise prompts once with `sudo -v` on `/dev/tty`. That prompt lives in this helper. The setup script then runs as the current user, so its own sudo calls reuse the warm timestamp. `privileged_changes_needed` runs before the Hyprland block and cannot see plugin setup commands without a second pass over the list; issue #18 also owns that area. Without a terminal, or when sudo cannot be primed, the helper prints the script path. A setup that is due and does not finish is stored with `pending: true` and runs on the next apply. That covers a deferral, a failed script, and a timeout. A finished setup runs again after this layer's `omarchy plugin update` moves `HEAD`, including when that command exits non-zero after the revision changes. A commit made by hand inside the checkout does not.

`update-all` is the only command that updates plugin checkouts. It passes `--update-plugins` into `apply-layer.sh`, which then calls the helper with `--update`. Configuration-only `groundwork-update` uses `--update` for saved setup choices and does not pass `--update-plugins`, so existing checkouts stay at their current revisions. Updates run `omarchy plugin update <id> --yes` for listed ids that are already installed. `omarchy update` does not update plugins.

Retired ids are removed with `omarchy plugin remove <id> --yes` only when this layer recorded the install. Every other retired id whose plugin directory exists gets one notice and stays on disk. The helper records that notice, and later runs stay quiet for that id. A retired id with no directory is left unmentioned. Removal still happens when the id is excluded. Without a shell session, installs, enables, updates, and removals are deferred and retried next run. One plugin failure prints a line and leaves the rest of apply running.

If `~/.config/hypr/mouse.lua` or `omacontrol.lua` sets `touchpad.natural_scroll` differently from the stowed `packages/hypr/.config/hypr/input.lua`, the helper warns. When `~/.config/hypr/hyprland.lua` requires `hypr.mouse` or `hypr.omacontrol`, the warning names the file loaded later; that file wins. When `hyprland.lua` does not load the differing file, the warning says so and the stowed `input.lua` still applies. The value read is the last `natural_scroll` inside the `touchpad` table. A missing key in the stowed file is upstream's `false`. See [decision 0007](0007-learn-omarchy-defaults.md).
